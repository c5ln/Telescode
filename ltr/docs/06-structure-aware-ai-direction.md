> 작성일 2026-09-13 · Issue #37 추천 실험 결과(`bench/RESULTS.md`)를 바탕으로 한 다음 단계 설계.

## 1. 출발점 — 지금까지 확인한 것

### 사용자 문제

코딩 에이전트를 쓰는 개발자 3명을 인터뷰했다. 공통점:

- 코드 작성은 빨라졌지만 **내용을 이해하기 어려워졌다**
- 낯선 함수의 역할을 파악하기 어렵다
- 설계 의도에 대응하는 구현을 찾기 어렵다

### 실험 결과 (`bench/RESULTS.md`, 229 인스턴스, `no_paths`)

| 항목 | 값 |
|---|---|
| deterministic baseline (0.6·PR + 0.4·BC) | MRR 0.128 |
| 제품 현재 출력 `file_rank` | MRR 0.054 |
| **LTR full (LambdaMART)** | **MRR 0.753, R@10 0.885** |
| semantic 그룹 gain 비중 | 약 76% |
| `-graph − full` | +0.024 (p=0.046) — 구조 신호는 순위에 추가 기여 없음 |

### 결론이 가리키는 방향

**구조 정보는 "고칠 파일을 찾는 순위"에는 기여하지 못했다.** 그러나 호출 흐름·상속·영향
범위처럼 **"코드가 어떻게 동작하는지 설명하는 뼈대"**로는 여전히 본래 역할이 있다.
이는 벤치마크가 잰 것(순위)과 다른 질문이며, 아직 검증되지 않았다.

→ 구조 정보의 쓰임을 **추천 순위에서 설명 근거로** 옮긴다.

## 2. 목표 — Telescode MCP + 화면 연동 설명

AI(코딩 에이전트)가 MCP로 Telescode 분석 DB를 조회하고, **파일·줄 번호를 근거로 코드를
설명하면서 Telescode의 zoomable UI를 설명 흐름에 맞춰 조작**한다.

```
사용자: "에이전트가 방금 만든 결제 재시도 로직이 어떻게 동작해?"
   │
   ▼
AI ── Telescode MCP 호출 ────────────────────────────┐
   │  1. locate("결제 재시도")      → 관련 함수·파일    │
   │  2. trace_calls(retry_payment) → 호출 흐름        │  SQLite DB
   │  3. describe(PaymentClient)    → 클래스 계층·필드  │  (파싱 결과)
   │  4. reading_order(목적)        → 읽을 순서         │
   └──────────────────────────────────────────────────┘
   │
   ▼
AI: 근거가 달린 설명
    "진입점은 checkout.py:42 submit() → payment.py:88 retry_payment() → ..."
   │
   ▼ focus_in_ui(retry_payment)
Telescode GUI: 모듈 → 함수 단위로 확대, 설명 중인 호출 경로 강조
```

### 왜 이 방향인가

| 관점 | 이유 |
|---|---|
| 사용자 문제와 일치 | 에이전트가 더 빨리 고치게 돕는 것이 아니라 **사람이 이해하게** 돕는다 |
| 실험 결과와 정합 | 순위에 기여 못 한 구조 신호를 설명의 근거로 쓴다 |
| 차별점 | 텍스트로 코드를 설명하는 AI 도구는 많다. **설명과 의존 그래프 화면의 동기화**는 Telescode만 가능하다 |
| 이미 가진 자산 | DB 스키마(`src/db/db.cpp`)에 `file`, `class`, `base_class`, `function`, `param`, `field`, `link`, `reading_sequence`가 있다. `function`/`class`에 `start_line`/`end_line`이 있어 `파일:줄` 인용이 가능하다 |

## 3. MCP 도구 설계

| 도구 | 설명에서의 역할 | DB 근거 | 상태 |
|---|---|---|---|
| `overview` | 저장소 구성, 주요 모듈, 중심 파일 | `file`, `reading_sequence` (PageRank/BC) | 데이터 있음 — **구조 지표가 제대로 쓰이는 곳** |
| `locate` | 개념·질문 → 관련 심볼 | BM25 (선택적으로 임베딩) | bench 코드 재사용 |
| `trace_calls` | 진입점에서 시작하는 호출 흐름 (깊이 제한) | `link`(CALLS), `function` | 데이터 있음 |
| `describe` | 위치, 파라미터, 상속, 필드, 복잡도 | `function`, `param`, `class`, `base_class`, `field` | 데이터 있음 |
| `impact` | 바꾸면 영향받는 곳 | 역방향 `link` | 데이터 있음 |
| `reading_order` | 목적에 따른 읽기 순서 | `reading_sequence` | 데이터 있음 |
| `explain_diff` | 에이전트가 방금 바꾼 코드 설명 | git diff → 바뀐 함수 → 호출 영향 | **신규** — 사용자 문제에 가장 직접적 |
| `focus_in_ui` | GUI에서 노드로 이동·확대·경로 강조 | GUI와 통신할 IPC | **신규** — C++ 쪽 작업 필요 |

### 구현 순서

1. **MVP:** `overview`, `locate`, `trace_calls`, `describe` — 기존 DB 읽기 전용
2. `explain_diff`
3. `focus_in_ui` (GUI 연동)

### 기술 결정 (미정)

- **서버 언어:** Python 권장. bench의 BM25를 재사용할 수 있고 SQLite는 읽기만 한다.
  현재 `bench/.venv`에 `mcp` 패키지는 설치되어 있지 않다.
- **대상 DB:** `pystdlib.db`로 개발, xarray DB로 평가.
- **임베딩:** MVP에서는 쓰지 않는다. 새 저장소마다 초기 비용이 든다
  (현재 코퍼스 기준 약 $0.97, 약 25분). 리랭커는 질의마다 비용이 든다.

## 4. 알려진 한계

| 한계 | 영향 | 대응 |
|---|---|---|
| Python 정적 호출 분석의 불완전성 (동적 디스패치, `getattr`, 데코레이터) | 호출 그래프가 틀리면 **설명도 자신 있게 틀린다** | 도구 응답에 "정적 분석 기준, 누락 가능" 명시. `link` 정밀도를 샘플로 측정 |
| `link` 테이블에 호출 발생 줄이 없음 | "어느 줄에서 호출하나"를 인용할 수 없음 | 함수 범위까지만 인용하거나 호출 위치 컬럼 추가 |
| 파서가 Python 전용 | 다른 언어 저장소 불가 | 범위를 Python으로 명시 |
| 유사 도구 존재 (LSP 기반 심볼 탐색 MCP 등) | "왜 만들었나" 질문 | 차별점: 읽기 순서 + 목적 기반 추천 + GUI 동기화 |
| 에이전트 효과 ≠ 사람 효과 | 자동 지표를 사람의 이해로 바꿔 쓰면 안 됨 | 사람 효과는 3명 과제로 따로 확인 |

## 5. 검증 설계 — 실사용자 없이

설명이 "좋은가"는 재기 어렵다. 대신 **틀렸는가**와 **이해를 도왔는가**를 잰다.

| 방법 | 방식 | 지표 | 자동화 |
|---|---|---|---|
| ① 사실 정확도 | 설명 속 주장("A가 B를 호출한다", "X는 Y를 상속한다")을 뽑아 DB·소스와 대조 | 환각률 | 가능 |
| ② 이해도 퀴즈 | DB에서 정답이 확정되는 문항 자동 생성 ("`foo`를 바꾸면 영향받는 파일은?", "`Bar`의 부모 클래스는?") | 정답률 | 가능 |
| ③ 근거 인용률 | 설명 문장 중 `파일:줄` 근거가 달린 비율, 인용이 맞는 비율 | 인용률 | 가능 |
| ④ 3명 과제 | 에이전트가 작성한 PR을 주고 이해 과제 수행 | 시간, 막힌 지점, 소감 | 사람 |

### 비교 조건

- **기준:** 같은 모델이 MCP 없이 파일만 읽고 설명
- **처리:** 같은 모델 + Telescode MCP
- 정답은 DB에서 확정되므로 LLM이 LLM을 채점하는 순환이 없다. 단 호출 그래프가 놓친
  관계(동적 호출 등)는 정답 문항에서 제외하고, 그 기준을 기록한다.

### 3명 과제 설계 (UI 효과 확인)

- 난이도가 비슷한 PR 과제 두 개: 하나는 **글로만 된 설명**, 하나는 **화면 연동 설명**
- 조건 순서를 사람마다 바꿔 학습 효과 상쇄
- 기록: 호출 흐름을 따라가 설명하는 데 걸린 시간, 막힌 지점, 소감
- 3명이므로 통계를 내지 않는다. **정성 결과로만** 보고한다.

## 6. 함께 검토했던 다른 후보

| 후보 | 판단 |
|---|---|
| **저장소 간 일반화** (xarray로 학습 → pytest로 평가, 반대도) | **비용 0원.** 필요한 피처·seed가 전부 로컬에 있다(`features_all_embedppr.csv` 43,688행). `model.py` fold 배정만 `repo` 기준으로 바꾸면 된다. 주의: PPR seed 설정(`topk1_pow1`)은 두 저장소를 합친 train에서 골랐고, 리랭커 모델 선택에 쓴 40개 인스턴스의 저장소도 확인 필요 |
| 리랭커 후보 수 N 곡선 (N=10/20/30/50) | 단독으로는 약함. ① 로그상 `tokens=0 cost=$1.0680` — 요금이 질의 단위일 가능성이 높아 N을 줄여도 비용이 거의 안 줄 수 있다 ② 줄이는 방향은 결과가 예측 가능 ③ 절대 금액이 작다. **N>50 + 지연시간** 형태일 때만 의미 있음 |
| 에이전트 작업 효율 A/B (MCP 유무로 SWE-bench 풀이) | MCP가 생기면 함께 할 수 있다. 다만 목표가 "사람의 이해"이므로 부차 지표로 둔다 |
| 커밋 동시 변경·새 기여자 첫 PR을 대리 라벨로 | 데이터 확장과 "전체 구조 파악" 목적의 라벨로 유용. 후순위 |
| 구조 신호 살리기 (호출 거리, 모듈 응집도) | 실패 가능성이 높아 마감 전에는 비추천 |

## 8. 지원서 4번 문항 초안 (구현 완료 가정)

> 문항: 지원한 직무 관련 본인이 갖고 있는 전문지식/경험(심화전공, 프로젝트, 논문, 공모전 등)을
> 작성하고, 이를 바탕으로 본인이 지원 직무에 적합한 사유를 구체적으로 서술 (1000자 이내)
>
> 공백 포함 882자 / 공백 제외 685자.
> ⚠ **`〔 〕` 안의 수치와 3명의 답변 내용은 가상이다.** 실제 측정값으로 바꾸기 전에는 제출하지 않는다.
> 나머지 수치(229개, 0.128→0.753)는 `bench/RESULTS.md`로 확인한 실제 값이다.

**[코드 구조를 보여주며 설명하는 AI]**

코딩 에이전트를 쓰는 개발자 3명을 인터뷰한 결과, 코드 작성은 빨라졌지만 낯선 함수의 역할과 설계 의도에 대응하는 구현을 찾기 어렵다는 공통점이 있었습니다. 이를 위해 코드 탐색 도구 Telescode에 파일·함수·호출 관계를 분석해 저장하는 기능과 의존관계를 확대·축소하며 탐색하는 UI를 구현했습니다.

작업 목적에 맞는 파일을 추천하기 위해 GitHub 이슈와 PR 수정 파일로 학습 데이터를 구성하고, 이슈 본문의 파일 경로 제거와 이슈 단위 교차검증으로 평가 누수를 막았습니다. 구조 지표와 BM25·임베딩·리랭커 특징을 결합한 LambdaMART는 229개 이슈에서 MRR을 0.128에서 0.753으로 높였지만, 구조 신호는 순위에 추가 기여가 없었습니다. 구조 정보는 파일을 찾기보다 흐름을 설명하는 데 써야 한다고 판단했습니다.

그래서 Telescode를 MCP 서버로 제공했습니다. AI는 호출 흐름과 영향 범위를 조회해 설명하면서, Telescode 화면을 모듈에서 함수 단위로 확대하고 설명 중인 호출 경로를 강조합니다. 설명 문장과 코드 구조가 같은 화면에서 이어집니다. 분석 DB에서 정답이 확정되는 이해도 문항 〔200〕개로 파일만 읽고 설명한 경우와 비교해, 잘못된 호출 관계 주장을 〔23.4〕%에서 〔6.1〕%로 줄였습니다. 인터뷰했던 3명에게 에이전트가 작성한 PR 이해 과제를 맡기자, 〔글로만 된 설명보다 화면 연동 설명에서 호출 흐름을 더 빨리 따라갔다는 답〕을 얻었습니다.

이 경험은 AX/PI센터의 RAG 기반 서비스 개발과 지식 모델링 업무와 맞닿아 있습니다. 현장의 어려움을 요구사항으로 정의하고, 신뢰할 수 있는 데이터와 정량 지표로 AI 서비스의 정확성과 효용을 검증하는 엔지니어가 되겠습니다.

### 작성 원칙

- **결과가 기대보다 나빠도 그대로 쓴다.** 2문단이 이미 "가설이 틀렸음을 인정한" 글이라 톤이 맞는다.
- **3명 결과는 통계처럼 쓰지 않는다.** 시간 수치는 면접에서 표본 크기와 함께 말한다.
- **비교 기준을 분명히 한다.** "같은 모델이 MCP 없이 파일만 읽고 설명한 경우".
- **"AI가 직접 만든 UI"라는 표현은 쓰지 않는다.** AI가 UI를 만든 것으로 읽힐 수 있다.
- **UI는 차별점 한 문단으로만.** 직무 핵심은 데이터·AI 서비스·검증이다.
- 파싱 병렬화(3,120ms → 1,264ms, `src/parser/BENCHMARK.md`)는 흐름에서 벗어나 뺐다.
  "대용량 데이터 처리·성능 분석" 근거로 면접이나 다른 문항에서 쓴다.

### 면접 예상 질문

- 구조 신호가 쓸모없었다면 그래프 기능은 왜 필요한가? → 순위가 아니라 설명·시각화·온보딩용
- 무엇과 비교했나? 정답은 어떻게 믿을 수 있나? → §5 비교 조건과 정답 문항 제외 기준
- 리랭커 비용은 제품에서 감당 가능한가? → 229 질의 $1.07, 질의마다 계산이라 캐시 불가
- 3명으로 무엇을 말할 수 있나? → 자동 지표가 사람에게도 들어맞는지의 정성 확인
