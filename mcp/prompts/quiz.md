# Telescode tour quiz instructions

목적은 사용자가 투어의 한 정차 지점에서 본 코드를 **개념적으로** 이해했는지 확인하는 것이다. 문제는 그 코드베이스에 합류한 개발자가 기술 면접에서 받을 법한 질문처럼 쓴다. 퀴즈 결과는 이해도 자체가 아니라 이해 상태를 추정하기 위한 관측값으로 저장된다.

## Context 구성 (GraphRAG)

1. `open_project`로 투어와 같은 DB를 연다.
2. 난이도마다 `get_quiz_context(projectId, nodeId, difficulty)`를 호출한다. 이 결과가 해당 난이도 문제가 사용할 수 있는 유일한 근거이다.
   - `excerpts`는 실제 소스 코드이다(줄 번호 포함). 문제는 주로 여기서 나온다.
   - `relations`는 코드 그래프(포함, import, 클래스 관계)이고, `nodes[].facts`는 시그니처 같은 구조 정보이다.
   - `learning`은 reading sequence 기반 학습 순서이다. import 관계를 학습 선행 관계라고 단정하지 않는다.
3. `excerpts`가 비어 있으면(소스를 찾지 못한 프로젝트) 시그니처와 관계로 답할 수 있는 개념 문제만 만들고, 그것도 어렵다면 해당 난이도는 만들지 않는다.

## 쓰지 말아야 할 문제

다음은 이해도를 보여주지 않으므로 **절대** 묻지 않는다.

- 개수: 파일·클래스·메서드·import 수, 줄 수
- 지표: 복잡도, 순위, 점수
- 단순 위치/이름 확인: "X는 어느 파일에 있는가", "X의 메서드 이름은 무엇인가", "X는 Y를 import하는가"
- 코드 한 줄을 그대로 옮겨 적으면 답이 되는 문제

## 난이도 = 면접 레벨

난이도는 사용자의 숙련도가 아니라 문제가 요구하는 추론 깊이, 연결해서 봐야 하는 범위, 추상화 수준이다.

- **easy — 신입(newbie)**: 이 코드 하나를 읽고 *무엇을, 왜* 하는지 설명할 수 있는가.
  - 이 클래스/함수가 맡은 책임은 무엇인가?
  - 이 입력(또는 상태)이면 이 함수는 어떤 결과를 내는가?
  - 이 조건문/예외 처리는 어떤 경우를 막기 위한 것인가?
- **medium — 주니어(junior)**: 직접 연결된 코드와 함께 *흐름*을 따라갈 수 있는가. 근거 노드 2개 이상.
  - A가 B를 호출(상속, 사용)하는 이유는 무엇이고, 그 과정에서 데이터는 어떻게 바뀌는가?
  - 이 버그 증상이 나타났다면 어느 부분을 먼저 의심해야 하는가?
  - 이 값은 어디서 만들어지고 어디서 소비되는가?
- **hard — 시니어(senior)**: 여러 요소를 종합해 *설계*를 판단할 수 있는가. 근거 노드 2개 이상, 가능하면 관계를 둘 이상 엮는다.
  - 이 검사/캐시/추상화를 제거하면 어떤 문제가 생기는가?
  - 이 구조를 택한 이유(트레이드오프)는 무엇이고, 대안은 무엇이 더 나빴을까?
  - 새 요구사항(예: 새 출력 형식, 새 백엔드)을 추가하려면 어디를 확장해야 하는가?
  - 동시성·오류 전파·성능 측면에서 이 설계의 약점은 무엇인가?

## 문제 작성

- 유형은 `multiple_choice`(오답 2–4개) 또는 `true_false`(정답 "True"/"False")만 쓴다. 객관식을 기본으로 하고, true/false는 흔한 오해를 검증할 때만 쓴다.
- 질문은 상황이나 이유를 묻는 문장으로 쓴다. 코드 식별자는 필요한 만큼만 쓰고, 정답이 질문 문장에 드러나지 않게 한다.
- 오답은 실제로 헷갈릴 만한 오개념으로 만든다(예: 책임을 옆 클래스와 혼동, 호출 방향을 반대로 이해, 예외를 잘못된 계층에서 처리한다고 생각). 길이와 어조를 정답과 비슷하게 맞추고, "모두 정답" 같은 선택지는 쓰지 않는다.
- 정답은 `excerpts`·`relations`·`facts`로 확인 가능해야 한다. 코드에 없는 동작, 외부 라이브러리 내부 구현, 작성자의 의도를 근거 없이 단정하지 않는다. 설계 의도를 묻는 문제는 코드에서 관찰되는 결과(무엇이 가능해지고 무엇이 막히는지)로 답할 수 있어야 한다.
- `concept`에는 확인하려는 개념을 짧게 쓴다(예: "책임 분리", "요청 재시도 흐름", "결과 객체의 불변성").
- `explanation`은 왜 정답인지와 대표 오답이 왜 틀렸는지를 2–3문장으로 설명하고, 근거 코드를 `파일:줄` 형식으로 인용한다(예: `sherlock_project/notify.py:120`).
- `evidenceNodeIds`는 해당 난이도 context의 nodeId만 쓰고, 정차 노드를 반드시 포함한다.
- 근거 있는 좋은 문제를 만들 수 없다면 그 난이도는 만들지 않는다. 억지로 채우기 위해 위의 금지 유형으로 돌아가지 않는다.

## 저장

`create_quiz`에 투어 ID, revision, 정차 인덱스, nodeId와 함께 저장한다. 검증 오류가 나면 근거를 고쳐 다시 저장한다. 에이전트는 퀴즈에 답하거나 응답을 기록하지 않는다.
